A small team edited the same shared document on several laptops while they were offline. Each laptop saved a log of the edits it made, and when they reconnected the logs got copied around between them, so the same edit often shows up in more than one log and the lines are out of order. Replay all of it and produce the one document state that every laptop will agree on once syncing settles.

Each file in `/app/data/replicas/` is one laptop's log, named `<replica_id>.log` where the id is an integer. Every line is a JSON object like `{"replica": 2, "seq": 5, "vv": {"1": 3, "2": 4}, "ts": 17, "op": {...}}`. `replica` is the laptop that made the edit and `seq` is that laptop's own edit counter (1, 2, 3, ... in the order it made them). An edit is named by the pair `(replica, seq)`; the same pair may appear in several logs but it is one edit, and applying it more than once does nothing. `vv` gives, per laptop id written as a string, the highest `seq` from that laptop the author had already applied when it made this edit. `ts` is an integer clock. `op` is the edit, one of `{"op":"set_add","elem":<str>}`, `{"op":"set_remove","elem":<str>}`, `{"op":"reg_set","value":<str>}`, `{"op":"seq_insert","id":<str>,"after":<str|null>,"value":<str>}`, or `{"op":"seq_delete","id":<str>}`, where each `seq_insert` has a unique `id` and `after` is the id it was placed just after (`null` means the front of the list).

Write `/app/merge.py` so that running `python3 /app/merge.py` reads every log and writes the merged document to `/app/result.json`. The document is a set of tags, one register string, and an ordered list. An edit can be applied only once every edit it depends on has been applied: it depends on `(r, 1..vv[r])` for each `r` in its `vv`, plus its own earlier edits `(replica, 1..seq-1)`. Drop any edit whose dependencies never all arrive. Treat one edit as visible to another when it is one of that edit's dependencies. Your answer must come out the same no matter what order you read the files or apply the edits.

A tag belongs to the set when at least one `set_add` for it is not visible to any `set_remove` for it (add wins). The register holds the `value` of the `reg_set` with the largest `ts`, and a tie on `ts` goes to the larger `replica`. For the list, each inserted element sits immediately after the element its `after` names (or at the front when `after` is null), and when several inserts share the same `after` they go in order of their `id` compared as strings from larger to smaller, so the larger `id` sits closer to that anchor. A `seq_delete` hides its element from the list, but the hidden slot still anchors any insert that points at it.

Write `/app/result.json` as one JSON object with exactly four keys. `set` is the surviving tags as a JSON array of strings in ascending order. `register` is `{"value": <str or null>, "winner": [ts, replica] or null}` for the winning `reg_set`, or value `null` and winner `null` if no `reg_set` was applied. `sequence` is the visible element values in list order as a JSON array of strings. `applied` is the integer number of distinct edits that were applied.
